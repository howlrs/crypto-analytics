## 2. 分析C: 東証の暗号資産関連株は BTC/ETH に先行するか

**問い**: PR #14・#15 は日本のマクロ・需給指標を検定したが、暗号資産に直接つながる東証の銘柄は見ていない。日本の個人は、税率の違いや
証券口座の利便性から上場株を通じて BTC の値動きを買う。トレジャリー企業はその需要を増資で受け、BTC 購入に換える。この需要が先に立つなら、
BTC と TOPIX で説明できない当該銘柄の上昇は、その後の BTC の上昇につながる。

**利益源泉**: 東証で先に動く需要に遅れて反応する、暗号資産市場の参加者。ただし経路の大きさは BTC の出来高に対して小さく、事前確率は低い。

**銘柄（リターンを見る前に公開情報で固定）**

| バスケット | 銘柄（開始日） |
|---|---|
| treasury | Metaplanet 3350（2024-05-13、BTC を財務戦略に採用）、Remixpoint 3825（2024-09-26、初回購入）、ANAP 3189（2025-04-01、開示で確認できた最も早い購入の月） |
| exchange | Monex 8698（Coincheck）、SBI 8473（SBI VC Trade など）、GMO インターネットグループ 9449（GMO コイン）。いずれも 2021-01-04 から |

開始日より前の日は、その銘柄の回帰にも入れない。Metaplanet と Remixpoint の日付は公開情報からの記憶で、今回は一次資料で確かめていない。

**シグナル**: 東証の各営業日 d について、銘柄の終値間対数リターン（分割調整）を、同じ時計の区間の BTC リターンと TOPIX リターンに回帰する。
係数は d の前の60営業日だけで推定し（最低40日）、d の残差をその回帰の残差標準偏差で割る。バスケットのシグナルは、その日に計算できる銘柄の平均。

**目的変数**: d の大引けから次の営業日の大引けまでの BTC・ETH の対数リターン（Binance perp の1分足）。大引けは 2024-11-01 まで 15:00 JST、
2024-11-05 から 15:30 JST。期間は目的変数の終点が 2026-08-01 より前まで（研究境界。`market.db` の終わりでもある）。

**検定と判定**

- 主ファミリー: {treasury, exchange} × {BTC, ETH} の4セル。目的変数をシグナルに OLS 回帰し、傾きの Newey–West（ラグ5）t から正の向きの片側 p を出す。
  Benjamini–Hochberg で補正する。
- 判定: q < 0.05、標本の前半・後半で傾きが正、2022-05・2022-11・2024-08 を除いても正、週次ではなく日次のルール（ポジション = clip(z, −1, 1)、
  回転1単位あたり 5bp）の平均損益が正、のすべてを満たすとき「先行する」とする。
- 副次（記述）: 目的変数を次の寄り付き（欧米時間の分）までに変えた同じ4セル。各銘柄と BTC の同時相関（前提の確認）。

**検出力**: treasury は約480日で、最も厳しい閾値（α/4）なら相関 0.10 で検出確率は約半分、80% には 0.14 が要る。exchange は約1,350日で、
それぞれ 0.06 と 0.08。日次でこの大きさの予測相関は大きく、**小さな効果は否定できない**。「売買判断に使えるほど大きな先行があるか」の判定である。

**結論の使い方**: 支持されなければ、J-Quants の暗号資産への経路（IV、TOPIX、需給、関連株）をすべて閉じ、この問いのためには再契約しない。

## 3. 分析D: 信用買いの群集は負けるか

**問い**: 採用済みの funding capture は「レバレッジをかけたロングが過大に払っている」という主張の上にある。暗号資産の履歴は約5年で、レジームも偏っている。
東証の信用残は10年分あり、銘柄ごとにレバレッジのロングの残高が分かる。ここで同じ主張を検定する。**売買戦略ではない**。日本株のロングショートは本プロジェクトの執行先にない。

**時刻**: 信用残は基準日（週の最終営業日）の2営業日後の 16:30 JST ごろに公表される。判断はその次の大引け（基準日の3営業日後）。`PubDate` が入っている期間は、
その翌営業日より早くしない。保有は次の判断の大引けまで。2026-09-28 以降の日次の行は使わない（週末の基準日だけ。研究境界の前なので本検定にはもともと入らない）。

**銘柄**: 判断日時点の銘柄マスタで内国普通株（`prod_cat` 011）、市場は TOKYO PRO MARKET とその他を除く。さらに終値100円以上、時価総額50億円以上、
直近20日の売買代金中央値2,000万円以上、基準日の信用残があること。上場廃止銘柄も在籍中は含む（生存バイアスなし）。

**リターン**: 分割調整の価格リターン。配当は Standard の対象外。配当は低信用残の大型株に多いので、D2・D3 には不利に働く。

**検定（主ファミリー、期待する符号はすべて負）**

| 記号 | 内容 | 利益源泉の読み |
|---|---|---|
| D1 | 信用買いの全体の建玉（各銘柄の買い残金額で加重）の翌週リターンを、時価総額加重の市場と規模要因（等加重 − 時価総額加重）に回帰した切片（アルファ） | レバレッジのロング全体が市場より負けているか |
| D2 | 銘柄ごとの翌週リターンを、買い残の時価総額比に横断回帰した Fama–MacBeth の傾き。対照: 対数時価総額、対数売買代金、直近20日リターン、その前の230日リターン、20日ボラティリティ、33業種（業種内平均を除去） | 他の特徴を除いても、レバレッジの偏りが負けにつながるか |
| D3 | D2 と同じで、シグナルを買い残の時価総額比の4週変化に替えたもの | 積み上がる最中のレバレッジが負けるか |

横断の変数は週ごとに1%/99%で丸めて標準化し、リターンは0.5%/99.5%で丸める。推論は週次の推定値の Newey–West（ラグ4）。Benjamini–Hochberg で3本を補正する。

**判定**: 各検定について、q < 0.05 かつ 2022-01 の前後で符号が負、かつ 2020-03 と 2024-08 を除いても負なら支持。3本すべてで `supported`、一部なら `partly_supported`。

**副次（記述、判定なし）**: 買い残比率の十分位スプレッド（生リターン）、最上位十分位と全体の差、信用売りの建玉のアルファ、貸借銘柄だけ・時価総額上位半分だけの D2、
TOPIX が5営業日で −4% 以下だった直後の週の D2（暗号資産で棄却した清算リバージョンの類比。強制売りの反発があるなら傾きは正に寄る）。

**検出力**: 週数は約490、各週の銘柄は約2,500。週次の傾きの t で判定するので、年率で数%の差を検出できる見込み。

**結論の使い方**: `supported` なら、「レバレッジのロングが負ける」は暗号資産固有の事情ではなく市場をまたぐ現象の証拠になる。funding capture の前提を強めるが、
BTC/ETH の収益の保証にはならない。支持されなければ、利益源泉の説明は funding の支払いそのものに限られ、「負ける相手」の一般論としては語れない。

## 4. 残す集計値（E）

`purge_jquants.sh` は `/mnt/e/Datas/market/jquants/` を丸ごと消すので、結果もそこに置くと一緒に消える。削除後も残すものは
`/mnt/e/Datas/market/japan_retained/`（リポジトリの外、削除の外、GCS 控えの外）に置く。`backtests/japan_retained.py` の検査を通らないものは書けない
（1銘柄1行、日付を含まない、60観測未満の統計を含まない、リストの長さに上限）。形を検査するだけで、規約への適合を保証するものではない。

**銘柄別リスクカード**（`backtests/japan_risk_cards.py`）: 直近250日の売買代金中央値の上位500銘柄と、日経225・TOPIX の ETF。項目は、前日終値からの最大上昇・最大下落、
99%の日次変化、夜間と日中のリターンとボラティリティ、決算日と他の日の平均変化、値幅制限に達した日の割合、TOPIX ベータ、H1 の規則で許されるレバレッジ（売り・買い）。
xyz に新しい日本株 perp が上場したときの、最初のレバレッジ判断の材料にする。東証の値幅制限で切られた値なので、perp のジャンプの下限として読む。

カードは**公開しない**。J-Quants のヘルプは自分の分析結果の公開を認めるが、元データを復元できない派生物を解約後も残せる条件は「外部に配信・公開しないこと」とされる。

## 5. J-Quants なしで H1 を追う（F）

H1 の台帳は東証終値を使うので、解約中は止まる。規則は変えない。ただし損益の大半は東証終値なしで分かる。乖離の項は日々足すと両端の乖離に縮むからで、
残りは Hyperliquid の funding と、perp の値動きだけで決まる清算判定である。

`backtests/japan_perp_monitor.py status` は同じ台帳コードに、公正価格の代わりに perp 自身の価格を渡す（乖離は0）。判定は出さず、受取 funding と清算余裕だけを示す。
`calibrate` は 15分足のある 2026-08-31 以降で公式の台帳との差を測る。これは公式の終値があるうちにしかできない。
