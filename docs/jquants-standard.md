# J-Quants Standard の活用: 取得データと追加分析

PR #14（`docs/japan-crossmarket.md`）で、J-Quants の日本 IV・TOPIX は BTC/ETH の1〜3日リスク判断に効かないと判定した。
本書はその続きとして、(1) Standard 契約で実際に取れるデータの棚卸し、(2) 暗号資産の執行先（Hyperliquid）で
日本の価格に連動する商品が取引できることの確認、(3) その二つを結ぶ追加分析の設計と結果をまとめる。
売買推奨ではない。BTC/ETH の封印済み registry、既存 results、`market.db` は変更しない。

## 2. Hyperliquid で日本の価格が取引できる

Hyperliquid の HIP-3 市場 `xyz`（trade.xyz）に、日本関連の perp が上場している（2026-10-20 の公開 API と
[trade.xyz の仕様](https://docs.trade.xyz/xyz-perps-specification)で確認）。

| 銘柄 | 参照 | 価格の単位 | 上場（funding 初回） | 最大レバ |
|---|---|---|---|---|
| `xyz:JP225` | 日経225（現物指数。現物時間外は先物から割り引いた推定値） | 円建て指数水準をそのまま USDC で精算（クアント） | 2026-04-09 | 20x |
| `xyz:KIOXIA` | 東証 285A | 円価格 ÷ リアルタイム USDJPY | 2026-06-25 | 10x |
| `xyz:SOFTBANK` | 東証 9984 | 同上 | 2026-06-26 | 10x |
| `xyz:JPY` | USD/JPY | — | 2025-12-23 | 50x |

- 個別株の外部価格は 8:20〜16:30 JST と 17:00〜23:59 JST に更新される。それ以外の時間と週末・祝日は、板の
  インパクト価格を追う内部 EMA（τ=30分）で動き、外部価格の再開と同時に戻る。
- funding は `0.5 × [平均プレミアム + clamp(金利 − プレミアム, ±0.05%)]` で毎時（基準は年率約5.5%）。
- 手数料は growth mode でテイカー 0.9bp、メイカー 0.3bp。KIOXIA は 2026-09-28 に1:3分割があり、建玉は東証終値で
  強制精算されて再開した。

これで J-Quants の役割が変わる。暗号資産の予測材料（PR #14 で否定）ではなく、
**ユーザーの執行先で取引できる日本の商品に対する、公式の参照価格と需給データ**として使える。

## 3. 分析A: 日本関連 perp の funding キャリー（実行可能性の記述）

**問い**: 採用済みの funding capture と同じ利益源泉（レバレッジをかけたロング需要が払う funding）が、
`xyz` の日本関連 perp にもあるか。東証の現物を持って perp を売る組み合わせは、どれだけ稼ぎ、どれだけぶれるか。

**利益源泉**: 東証に直接アクセスしにくい（あるいはレバレッジを求める）Hyperliquid 上のロングが払う funding。
相手方は明確だが、上場からの期間が短いため、**検定ではなく記述**にとどめる。

**本設計を書く前に見たもの**（記録）: 3銘柄の funding の全期間平均と週次合計（KIOXIA は上場後4週の週次合計が
94〜269bp、その後はおおむね週 −13〜+101bp。SOFTBANK と JP225 は正負に振れ、平均は基準付近）。
東証側の価格、ヘッジの乖離、ドローダウンは未計算。

**方法**（`backtests/hl_japan_carry.py`）

- 東証の各営業日 d の 15:30 JST（06:30 UTC）に評価する。perp と `xyz:JPY` の価格は 06:30 に始まる 15分足の始値、
  15分足がない日（概ね 2026-08-28 より前）は 06:00 の1時間足の終値（30分遅れ）。両方ある日で誤差を測る。
- 公正価格: 個別株は東証終値（分割調整なし）÷ USDJPY、JP225 はオプションの原資産価格。乖離 b = ln(perp / 公正価格)。
  |b| > 20% の日は株数基準の不一致（分割日など）として除外し、件数を出す。
- USD 建て損益（1日、空売り名目1あたり）: 個別株 = −Δb + 受取 funding。JP225 は現物側の円価値が残るので、
  同額の `xyz:JPY` ロングでヘッジし、その funding も含める（ヘッジなしも併記）。
- 期間: 全期間、上場後28日以降（post_launch）、2026-08-01 前後。費用は1往復
  （perp 0.9bp+1bp、東証 5bp、円転 5bp を片道で計上）。資金コスト、信用買いの金利、税、デプロイヤーリスクは含めない。
- 清算余裕: 終値間の1時間足高値から見た最大上昇を、隔離証拠金でレバレッジ L の空売りが耐えられる幅
  （1/L − 維持証拠金。維持証拠金は 0.5 ÷ 最大レバで近似）と並べる。

**判断の目安**（結果を見る前に固定）: post_launch で、1往復の費用控除後の年率が 10% 以上、かつ費用控除前の
Sharpe が 2 以上なら、2026-11 からの**事前登録つきペーパー追跡**の候補にする。どちらかを満たさなければ
「現時点では BTC/ETH の funding capture を上回らない」と記録する。

## 4. 分析B: 日本の需給・ポジション指標は日経225の翌週リターンを予測するか（事前登録）

**問い**: J-Quants Standard に固有の需給データ（投資部門別、信用残、空売り比率）が、Hyperliquid の
`xyz:JP225` で執行できる指数レベルの売買判断に情報を足すか。足さないなら、ユーザーの目的にとって
Standard の固有データの価値は低く、契約プランの見直し材料になる。

### 指標と事前に決めた符号

| 指標 | 定義（判断時点で公表済みのデータのみ） | 符号 | 想定する利益源泉 |
|---|---|---|---|
| S1 海外投資家フロー | 投資部門別（`TokyoNagoya`）の直近公表週の `FrgnBal / TotTot` | 正 | 価格を動かす海外勢の持続的な売買を、逆張りで受ける国内個人が遅れて受け渡す |
| S2 信用倍率 | 信用週末残高の銘柄別の買い残・売り残（株数）に、基準日の東証終値（分割調整なし）を掛けて全銘柄で合計し、ln(買い残金額 / 売り残金額) | 負 | 積み上がったレバレッジ買いは、追証と6か月の返済期限で将来の売り手になる |
| S3 空売り比率 | 33業種の合計（`9999` を除く）で (価格規制あり + なし空売り代金) / (実売り + 空売り代金) の、判断日前日までの直近5営業日平均 | 正 | 空売りの積み上がりは将来の買い戻し需要になる |

各指標は、直前52回の判断週の値（当週を含まない）の平均と標準偏差で z 化する。その52週のうち値がある週が
45週未満なら欠測。公表の遅れで基準日が判断日より14日超古くなった値も欠測とする。
空売り比率の構造的な上昇（規制変更や HFT の比率）を z 化で取り除くためでもある。

### 時刻

- 判断日: 各 ISO 週の最後の東証営業日の大引け。目的変数は、その日の日経225終値から次の判断日の終値までの対数リターン
  （重なりのない週次。オプションの原資産価格を使う）。
- 公表: 投資部門別は `PubDate` が判断日より前の週だけを使う（通常は判断日の前日以前）。
  信用週末残高は、基準日の2営業日後に公表されるので、その公表日が判断日より前の基準日だけを使う
  （J-Quants の `PubDate` が入っている期間は、それと2営業日後の遅いほう。初期の年は `PubDate` が空）。
  金額列（`LongVal` 等）も初期の年は空なので、全期間で株数×基準日終値の自前換算に揃える。
  空売り比率は判断日の前営業日までの日次値だけを使う。
- 期間: 52週の履歴がそろう 2017 年秋以降から、目的変数の終点が 2026-08-01 より前の週まで（研究境界）。

### 検定と判定規則

- 各指標について、翌週リターンを z に OLS 回帰し、傾きの Newey–West（ラグ4）t から、事前の符号方向の片側 p を出す。
- **主ファミリー**: S1〜S3 × 日経225 の3セルを Benjamini–Hochberg で補正。
- **判定**: q < 0.05、かつ前半（〜2021-12）と後半（2022-01〜）で傾きの符号が事前の向きと一致、
  かつ 2020-03 と 2024-08 を除いても一致、かつ週次ルール（ポジション = 符号 × clip(z, −1, 1)、
  回転1単位あたり 3bp の費用）の平均損益が正のとき、「その指標は `xyz:JP225` の判断に頑健な情報を持つ」とする。
  一つも満たさなければ「Standard 固有の需給データに、指数レベルで頑健な週次の情報は見つからない」。
- **副ファミリー**（記述）: 同じ3指標で BTC の翌週リターン（Binance perp、判断日 06:30 UTC から次の判断日 06:30 UTC）。
  PR #14 で日本→暗号資産の経路は否定済みなので、事前確率は低い。別に BH 補正する。
- 記述: 週次ルールの年別損益と Sharpe、一定ロングとの比較。funding は期間中に商品がなかったため含めない。

### 検出力

週次の標本は約450。片側5%で BH の最も厳しい閾値（α/3）なら、相関 0.10 程度で検出確率は約半分、
80% には 0.14 程度が要る。週次でこの大きさの予測相関は大きく、**帰無でも小さな効果は否定できない**。
大きく頑健な情報があるかどうかを判定する設計である。

## 5. 結果（2026-10-20 実行、集計値のみ）

### 結論

1. **J-Quants Standard 固有の需給データ（投資部門別・信用残・空売り比率）には、日経225の翌週リターンに対する
   頑健な情報は見つからなかった**（事前登録の判定）。BTC の翌週リターンにも何も足さない。
   空売り比率だけが事前の向きで片側 p = 0.021 だったが、BH 補正後 q = 0.063 で、効果はほぼ2022年以降に限られる。
2. **Hyperliquid の日本個別株 perp には、上場後に年率15〜30%台の funding が付いた**。売り側が受け取る形で、
   採用済みの funding capture と同じ利益源泉である。ただし、上場直後に符号が逆になる銘柄があり（SOFTBANK は最初の4週で
   売り側が年率約90%を支払った）、株価のジャンプが大きいので、perp 側のレバレッジは2〜3倍までに抑える必要がある。
   事前に決めた目安を満たしたのは SOFTBANK だけで、その合格も上場期間の除外に依存している（後述）。
3. 本書の範囲では、J-Quants は暗号資産の予測材料にも、日経225の需給シグナルにもならない。
   有効な使い道は、**Hyperliquid で取引できる日本銘柄の公式な参照価格（東証終値・分割）**に限られる。

### 分析A: 日本関連 perp のキャリー

| 銘柄 | 上場後28日 | 28日以降 | 2026-08-01以降 | 週次合計 p10 / p50 / p90（28日以降） | 負の週の割合（28日以降） |
|---|---:|---:|---:|---|---:|
| KIOXIA | +99% | +19% | +17% | 6 / 37 / 63bp | 8% |
| SOFTBANK | −90% | +32% | +29% | −32 / 39 / 186bp | 23% |

東証の現物を持ち perp を売った場合（USD 建て、日次評価、28日以降。JP225 は `xyz:JPY` で為替ヘッジ）

| 銘柄 | 日数 | 年率（費用前） | 1往復控除後 | 年率ボラ | Sharpe（費用前） | 最大DD | 目安 |
|---|---:|---:|---:|---:|---:|---:|---|
| KIOXIA | 58 | +15.7% | +14.7% | 18.0% | 0.87 | −5.8% | 不合格 |

- 東証終値時点の乖離 b の平均はほぼ0（KIOXIA +0.005%、SOFTBANK +0.002%、JP225 +0.04%）。
- 終値間の最大上昇（1時間足高値）は KIOXIA +32%（2026-07-31。東証終値は +17.7%）、SOFTBANK +18.7%、JP225 +7.1%。
  隔離証拠金の余裕は 4倍で約20%、3倍で約28%なので、KIOXIA は2倍、SOFTBANK は3倍が上限の目安になる。
  現物側を東証の現金買いにすると、必要資金は名目の1.5倍前後（2倍時）になり、資本あたりの利回りは表の約3分の2になる。
- 容量: 2026-10-20 時点の建玉は KIOXIA 約660万ドル、SOFTBANK 約120万ドル、JP225 約270万ドル。

**解釈上の注意（いずれも結果を見た後の確認で、判定には使わない）**

- 日次の損益のぶれは、15分足がない日に使った1時間足の代用価格（30分遅れ）で大きく見えている。|b| > 1.5% の日はすべて代用価格の日で、
  15分足で正確に測れた32日（2026-08-31〜10-19）の b の標準偏差は KIOXIA 0.39%、SOFTBANK 0.46%、JP225 0.11%。
  b の日次変化は負の自己相関（−0.06〜−0.42）を持ち、保有期間の終点の乖離リスクは ±1% 程度にとどまる。
- 同じ理由で、2026-08-01 以降の区間の数値は起点の日（07-31、代用価格）の乖離に強く影響される（KIOXIA で約 −4%）。
- 「上場後28日を除く」は KIOXIA の上場直後の高い funding を見て決めたが、SOFTBANK の上場直後のマイナス funding を除く方向にも働いた。
  上場時から売っていれば SOFTBANK は不利だった。SOFTBANK の合格は**証拠ではなく、将来追跡の候補**として扱う。
- 正確な終値時刻の価格は API が直近約52日分しか返さない。`data-tools/fetch_hl_xyz.py` は取得のたびに保存分へ統合するので、
  ペーパー追跡を始めるなら50日以内の間隔で実行する。

### 分析B: 需給・ポジション指標と日経225

標本: 判断週 465（2017-08-25〜2026-07-24、z がそろう週から）。日経225の値は FRED と最大相対差 0.0008%。
信用残の金額換算で価格が付いた銘柄は各週 95%以上（価格のない買い残株数は最大 0.2%）。

| 指標 | 事前の符号 | 週数 | 傾き（週次リターン / z） | HAC t | 片側 p | BH q | 前半 / 後半の傾き | 2020-03・2024-08 除外 | ルールの Sharpe | 判定 |
|---|---|---:|---:|---:|---:|---:|---|---:|---:|---|
| S1 海外投資家フロー | 正 | 455 | −0.07% | −0.58 | 0.72 | 0.72 | −0.01% / −0.13% | −0.11% | −0.16 | 支持せず |
| S2 信用倍率 | 負 | 461 | −0.06% | −0.57 | 0.28 | 0.42 | −0.17% / +0.08% | −0.02% | −0.18 | 支持せず |
| S3 空売り比率 | 正 | 461 | +0.21% | +2.03 | 0.021 | 0.063 | +0.02% / +0.50% | +0.24% | +0.46 | 支持せず |

- 判定: **頑健な情報なし**。一定ロングの週次 Sharpe は 0.79 で、どのルールもそれを下回る。
- S3 のルール損益は 2021〜2026 の6暦年すべてで正、2017〜2020 は4年中3年で負。効果は後半に偏っている。
  これを新しい仮説として扱うなら、2026-11 以降の将来データで事前登録して確かめる必要がある（本書では採用しない）。
- 副ファミリー（BTC、2021-01 以降の288週）: 片側 p 0.55〜0.73、q 0.73。日本の需給データは BTC の翌週リターンにも効かない。

### 実行後の変更

いずれも結果を見る前の、データ形式への対応。設計（指標・符号・時刻・判定規則）は変えていない。

## 7. 実行

```bash
cd /home/o9oem/workspace/crypto/analytics
data-tools/update_japan.sh --force   # 外部通信。経路確認 → fetch_hl_xyz → sync → build → japan_forward status → GCS 控え
data-tools/update_japan.sh --check   # 通信なし。VPN 経路の確認だけ
python3 backtests/hl_japan_carry.py            # 通信なし。出力は /mnt/e/Datas/market/jquants/results/hl_japan_carry
python3 backtests/japan_positioning.py         # 通信なし。market.db は read-only。出力は .../results/japan_positioning
```

- `update_japan.sh` は外部通信の前に、ホスト側 VPN の分割経路（0.0.0.0/1 と 128.0.0.0/1）が同じデバイスにあり、
  取得先がそこを通ることを読み取りだけで確かめ、満たさなければ何も取得せずに止まる。名前解決は IPv4 に固定する
  （`data-tools/ipv4_run.py`。この WSL では IPv6 だけが VPN を通らない）。引数なしなら前回成功から6日未満は何もしない。
  ログは `~/.cache/jquants-build/logs/`（J-Quants のデータを含まない）。xyz と J-Quants は独立して動き、J-Quants が拒否されても
  xyz の取得は続く（§9）。
- 個別に動かすときは `python3 data-tools/ipv4_run.py data-tools/fetch_jquants.py sync`、
  `python3 data-tools/fetch_jquants.py build --work-dir ~/.cache/jquants-build`。
  `--work-dir` に Linux 側のディレクトリを渡すと、/mnt/e に直接書くより速い（2026-10-31 の実測で 7分 対 24分）。

両分析スクリプトは入力と出力の SHA-256 を `manifest.json` に残す。出力には J-Quants 由来の日次・週次の値が入るので、
リポジトリには置かない（コードで拒否）。解約時は `/mnt/e/Datas/market/jquants/` 全体を削除対象とする。

## 8. DB の構成（2026-10-31 から）

`jquants.db`（約5GB）には、取得しているすべてのデータセットの全列が入る。定義は `fetch_jquants.py` の `TABLES`。

| 表 | 中身 | 主キー |
|---|---|---|
| `equities_daily` / `equities_valuation` | 株価日足（ストップ高安フラグ・`ExRT` を含む）/ 株価指標 | (date, code)、索引 (code, date) |
| `equities_master_history` と view `equities_master` | 銘柄マスタ。日次スナップショット1,022万行を、属性が変わるか欠けるたびに区切る有効期間 15,849行に圧縮。view は元の (date, code) 行をそのまま再現する | (code, valid_from) |
| `n225_options` / `n225_option_atm` | 日経225オプションの全行（緊急取引証拠金の発動日は 001 と 002 の両方）/ 満期ごとの ATM | (date, code, em_mrgn_trg_div) / (date, sqd) |
| `fins_summary` | 決算短信サマリー全111列。開示時刻は `HH:MM:SS` にそろえる（2018-03 までは `HH:MM`）、真偽値は 1/0 | (code, disc_no) |
| `fins_earnings_date` | 決算発表予定日。予定日が未定の公表（577行）も残す | なし |
| `margin_weekly` / `margin_alert` | 信用週末残（金額列を含む）/ 日々公表（公表理由の辞書を理由ごとの 0/1 列に展開） | (date, code) / (pub_date, code, app_date) |
| `short_positions` | 空売り残高報告。同じファイル内でまったく同じ報告が並ぶ例（184件）も残す | なし |
| `topix_daily`・`indices_daily`・`short_ratio`・`investor_types`・`trading_calendar` | 従来どおり（全列） | 従来どおり |
| `source_files`・`build_meta`・`build_quality` | 原本ファイル（行の `source_id` が参照）、作成時の集計、数値にできず NULL にした値の件数 | — |

- 既存の表名・列名は変えていない。新しい列は J-Quants V2 の列名の snake_case。
- 数値にできなかった値は捨てずに `build_quality` に数える（2026-10-31 時点では日々公表の `*`（比率算出不能）と `-`（前回なし）だけ）。
- 副索引を持つ表は rowid 表にし、`ANALYZE` もしない。WITHOUT ROWID 表に副索引があると、SQLite は
  `japan_positioning.py` の結合を「副索引の全走査 + 1行ごとの本体参照」で計画し、1,000万回のランダム読み込みで終わらなくなった。
  副索引のない表だけ WITHOUT ROWID にしている。
- 作り直しの検証（2026-10-31）: 全14データセットで、原本から独立に数えた行数（同じ日付は新しいファイルが置き換える）と一致した。
  分析が読む列は旧 DB と差分ゼロで、`hl_japan_carry.py` と `japan_positioning.py` の出力はバイト単位で同じだった。
- `sync` は一覧から消えたファイルを手元から消さない。Standard の提供範囲は過去10年なので、古い月が順に一覧から外れると
  見込まれ、契約中は手元の原本（約1.1GB）とその控えだけが写しになる。解約したらこれも消す（§9）。

### 控え（Google Cloud Storage）

- 原本と xyz の保存分を、非公開バケット `gs://crypto-bitflyer-418902-jquants`（gonumb66 のプロジェクト、asia-northeast1、
  公開アクセス防止を強制、オブジェクトの版管理あり、削除後7日の復元期間）に置く。2026-10-31 の初回で 1,823 ファイル・1.08GB が
  手元と一致した。DB（約5GB）は原本から作り直せるので置かない。
- `update_japan.sh` が週1回の更新の後に `gcloud storage rsync` で追加・変更分を送る（削除は伝えない）。Google 側のホストも
  VPN の経路を確かめ、IPv6 アドレスが返る場合は控えだけを飛ばす。控えの失敗は更新の失敗にしない（翌週の実行で追いつく）。
  無効にするには `JQ_GCS_URI=` を空にする。
- 復元: `gcloud --configuration=gonumb storage rsync gs://crypto-bitflyer-418902-jquants/jquants/raw /mnt/e/Datas/market/jquants/raw --recursive`
  の後に `fetch_jquants.py build`。J-Quants のデータは私的利用のライセンスなので、バケットを公開・共有しないこと。
  解約時は `purge_jquants.sh` が `jquants/` の全版を消す（§9）。

## 9. 解約と再契約

**解約したら J-Quants のデータをすべて消す。** J-Quants の公式ヘルプ（https://jpx-jquants.com/help/usage 、2026-10-31 確認）によると、
J-Quants はデータ販売ではなく利用サービスなので、解約・退会後は取得したデータ、その複製、元データを復元できる派生物をすべて削除する。
元データを復元できない派生物（集計統計など）は、外部に配信・公開しない限り残してよい。規約本文と食い違えば規約が優先する。

- 解約の効力が生じた後（API が拒否するようになった後）に実行する。
  ```bash
  data-tools/purge_jquants.sh         # 一覧だけ（GCS の一覧は VPN 経路の確認後）
  data-tools/purge_jquants.sh --yes   # 削除
  ```
  消すもの: `/mnt/e/Datas/market/jquants/`（原本・`jquants.db`・J-Quants 由来の値を含む results）、作りかけの DB、
  GCS の `jquants/` の全版（復元期間を先に無効にする）。残すもの: Hyperliquid のデータ（J-Quants ではない）、コード、文書、
  事前登録の registry（規則のみ）、文書中の集計値。
- **自動削除（2026-10-31 に設定済み）**: `~/.cache/jquants-build/jquants-cancel-requested` があると、契約期間が終わって API が
  拒否した最初の週次実行で `purge_jquants.sh --yes` まで行う（失敗したら毎時やり直す）。解約を取り消したり、プランを変えて
  契約を続けたりする場合は、このファイルを消す。アクセスが戻れば（再契約）自動で消える。GCS の削除処理は 2026-10-31 に試験用の
  場所で確かめた（全版が消え、復元待ちも残らない。バケットの復元期間はこの時点で無効にした）。
- 他のプロジェクトの J-Quants データは消さずに一覧に出す。2026-10-31 時点で `~/workspace/stocks/research/data/jquants`（3.1GB）。
  そのプロジェクトの results 等も含めて、そちらで消す。
- 解約後も `update_japan.sh` は動き続ける。xyz は毎週取得し（15分足は約52日分しか遡れないので、再契約後に H1 を評価するために要る）、
  J-Quants は毎週アクセスを確かめる。拒否されれば何も変えずに（空のデータディレクトリも作り直さない）
  `~/.cache/jquants-build/jquants-access-denied` に日付を残し、ログに削除の案内を出す。GCS には xyz だけを送る。
- **再契約したら**: 新しい API キーを `.env`（`JQUANTS_API_KEY`）に入れて `data-tools/update_japan.sh --force`。`sync` は一覧の
  全ファイルのうち手元にないものをすべて取り直す（約1,800ファイル・1.1GB、1秒1リクエストで30〜40分）ので、解約中の期間も埋まる。
  続いて build（約7分）、`japan_forward.py status`、GCS への控えが走る。提供範囲は過去10年なので、それより古い月は戻らない。
- `sync` は、どれか1つのデータセットでも 401/403 なら何もダウンロードせずに終了コード 3 で止まる。Free や下位プランのファイルが
  混ざらないようにするためで、プランを変えて一部だけ取るときは `--datasets` で明示する。
