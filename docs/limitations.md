# 解釈上の注意・既知の限界

hl-watch (`hl_watch.py`) の出力を解釈する際に留意すべき点。既存 `hl-watch/README.md`
「既知の制約」節と重複しない、より上位の解釈レベルの注意点をまとめる。

## 観測サンプルバイアス

hl-watch の母集団は **「発見済みアドレス」** (`recentTrades.users` 経由で発見し `CandidateSet`
LRUに乗ったアドレス、上限300・TTL30分) であり、市場全体のOI (建玉) ではない。具体的には:

- 直近の約定に登場したアドレスしか対象にならない。長期間ノートレードの大口ポジション保有者は
  `recentTrades` に現れない限り発見されない
- LRU上限300・TTL30分のため、アクティブでないアドレスは定期的にパージされる
- **TWAPを撃つアクティブ大口に偏る** — これはツールの設計目的 (プレ取引対象者リストの把握) には
  合致する長所だが、「観測された清算ウォールの合計 = 市場全体の清算ウォール」という解釈は誤り

`levels`/`analyze §3.5` の出力には毎回「観測サンプルベースであり市場全体のOIではない」旨が
自動的に付記される (`render_liq_levels_ladder`, hl_watch.py:1480-1482)。

## 清算価格は動的

`clearinghouseState.liquidationPx` は Hyperliquid のcross margin (口座全体) で決まる値であり、
以下の要因で刻々変化する:

- 証拠金の追加・引き出し
- 同一口座の他ポジションの含み損益 (cross margin なら全ポジション合算で証拠金計算)
- レバレッジ設定の変更

hl-watch は `watch_positions` へ**60秒毎 (active TWAP保有者) または5分毎 (それ以外)** の
スナップショットとして蓄積しており、瞬間値の時系列として扱うべきで、「その価格に到達すれば
必ず清算される」という固定値としては扱えない。`liqPx` が `NULL` のケース (低レバレッジ・
ヘッジ時) は `levels`/`analyze §3` の対象から自動除外される。

## アドレス ≠ 主体

1つの実運用主体 (トレーダー・ファンド) が以下を使い分けている可能性がある:

- サブアカウント (Hyperliquidのsub-account機能)
- 複数ウォレット
- APIウォレット (取引専用鍵)

hl-watch はアドレス単位で追跡しており、**名寄せ (同一主体の複数アドレスの統合) は未実装**。
「§3.5清算ウォール要約」等の集計値は名寄せ前のアドレス単位合計であり、実際に清算されるロットの
実効的な集中度は表示値と異なりうる。

## 他venueヘッジは不可視

Hyperliquid上のポジションが清算価格に近接していても、そのアドレスの主体が他取引所 (Binance、
Bybit等) で反対方向のヘッジポジションを保有していれば、実際の清算による市場インパクトは
hl-watch単体の解釈より小さい可能性がある。hl-watchはHyperliquidのオンチェーン情報のみを
参照しており、他venueの建玉は一切観測できない。

## レート推定の限界

`analyze` §1/§2 の実行レート ($/min) は「直近5分の実際の約定 (`twap_fills`) からの逆算」であり、
TWAP開始5分未満のものは意図的に除外される (`ANALYZE_NEW_TWAP_WINDOW_S=300秒`)。それでも
開始5分〜数十分程度の初期段階では、TWAPのペーシング変動やスライス間隔のばらつきにより
レート推定は大きくブレる。長時間 (declared_minutes が長い) TWAPほどレート推定は安定する。

## 清算判定はoracle/mark価格基準

hl-watchが参照する `liquidationPx`・`allMids` の mark価格は Hyperliquid の **oracle/mark価格**
ベースであり、板の最終約定価格 (last price) とは別概念。清算トリガー自体もHyperliquid内部の
mark価格基準で行われる仕様のため、本ツールの `levels` ラダーが示す「mark ± N%」もこの
oracle/mark基準で解釈する必要がある。

## CEXの清算ヒートマップとの信頼度の違い

Coinglass等のCEX清算ヒートマップは、公開されていない個々のポジションの清算価格を
「OI変化 + 想定レバレッジ分布」から**逆算・推定**したものであり、実際の建玉明細に基づくものではない。

対して hl-watch の `levels`/`analyze §3` は Hyperliquid の `clearinghouseState` API が返す
**実際の `liquidationPx` を直接観測**した値であり (推定ではない)、この点で情報の質が異なる。
ただし「観測サンプルバイアス」の節で述べた通り、hl-watchは発見済みアドレスのみのサンプルである
点には注意が必要 — 「個々の値の精度は高いが、母集団カバレッジは限定的」という、CEXヒートマップ
(母集団は市場全体だが個々の値は推定) とは逆の性質のトレードオフを持つ。

## イベント戦略バックテストの制約

`liq_reversion.py`/`crowding_signals.py` とその頑健性検証は、利用可能な1分足始値、固定のコスト仮定、
単一ポジションの重複排除に基づくイベントスタディである。板の深さ、注文分割、約定失敗、資金調達・
借入、サイズに伴う市場インパクトは含まない。2025年の時系列holdoutも事後に固定した retrospective
な評価であり、将来時点で封印された実験ではない。月cluster数が少ない戦略やレジームの区間・p値は
不安定になり得るため、FDR補正後にも実運用の収益性や将来の再現性を保証しない。

## 将来検証の制約

`prospective_validation.py` は上記のretrospective holdoutとは別に、2026-10-01以降のデータを対象とする
封印評価を追加する。ただし登録時の厳格なprimary ruleを通った候補は0件であり、17件のshadowは
非確認的な追跡にすぎない。shadowの良好な結果を後から確認結果へ読み替えたり、自動昇格させたりしては
ならない。最終結果にも、簡略コスト、単一ポジション、月cluster bootstrap、CEXデータ品質という上記の
制約は残る。

registryとsource manifestのSHA-256は偶発的な変更や古い成果物の混在を検出するが、署名や外部timestamp
ではない。観測開始前のGit commit/tag等に固定しない限り、第三者に対する暗号学的な改ざん不能性は
主張できない。必要期間にkline/OI/fundingの欠損が残る場合、評価器は統計を開示せずfail closedするため、
予定日に必ず結論が得られるとも限らない。

また、source event CSVは個別収益を含むので、観測期間中にsource分析を再生成すると評価器を介さず
途中成績を算出できる。両sourceスクリプトはregistryを検証し、2027-10-04 01:00 UTCまで評価期間を含む
再生成を機械的に拒否し、registryとsidecarの片方または両方が欠落した場合にもfail closedになる。ただしこれはOSレベルの暗号学的アクセス制御ではなく、コード自体を改変できる
管理者まで遮断するものではない。Gitに固定したコード・registry・再現性マニフェストを外部アンカーとして
監査し、観測中はDB収集だけを続ける必要がある。
